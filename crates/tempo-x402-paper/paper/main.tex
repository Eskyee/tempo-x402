\begin{abstract}
We ask how much a 0.5B-parameter open-weight coding model can improve on Rust code generation when its only training signal is the Rust toolchain itself---no human labels, no teacher distillation, no reward model. We introduce \textsc{Opus-201}, a 201-problem Rust benchmark stratified across six difficulty tiers, where every problem is a self-contained Cargo crate scored by \texttt{cargo test}. Starting from Qwen2.5-Coder-0.5B-Instruct (pass@1 $= 3/201 = 1.5\%$), a single round of full supervised fine-tuning on the model's own compiler-verified solutions reaches $33/201$ ($16.4\%$) at pass@1 and $52/201$ ($25.9\%$) at pass@5---a $17\times$ relative lift at pass@5, produced on a single RTX 3090 with zero humans in the training loop. The benchmark, the training data, and a single-command reproduction are released with this paper.
\end{abstract}

\section{Introduction}

Self-play and self-instruction have produced large improvements on small models for reasoning and code tasks \cite{zelikman2022star,wang2022selfinstruct}, but nearly all published code-domain results use Python unit tests as the verifier \cite{chen2021evaluating,austin2021program}. Rust offers a quantitatively richer signal. Before a single test runs, the Rust compiler rejects programs that fail to parse, fail to type-check, violate ownership rules, or fail the borrow checker. On base Qwen2.5-Coder-0.5B, $173$ out of $201$ first-shot solutions on our benchmark never reach the test stage---they are eliminated at compile time.

The question we study is narrow and concrete: how much does that free, structural verification signal buy when it is the \emph{only} signal? Concretely: can a 0.5B-parameter open-weight model, trained exclusively on its own solutions that compiled and passed tests, learn meaningful Rust competence?

Our answer is: yes, measurably so. With a single round of full supervised fine-tuning on 122 self-generated compiler-verified solutions, the base model's pass@1 rises from $3/201$ to $33/201$, and its pass@5 at temperature $0.7$ rises to $52/201$. The gain is uniform across T1--T3 tiers, absent on T4--T6 (which the base model cannot seed), and accompanied by a clean diagnostic shift: compile-failures fall from $173$ to $108$ while test-failures \emph{rise} from $8$ to $23$, exactly the signature of a model that has learned to produce well-typed Rust but not yet correct Rust.

\paragraph{Contribution.} We report the first published open-weight fine-tune of a Qwen2.5-Coder variant that targets Rust specifically, using only the Rust toolchain as verifier. The release includes \textsc{Opus-201}, the full self-play harness, the 122-example training set, and four GGUF checkpoints reproducing every row of Table~\ref{tab:main}.

\section{Benchmark}
\label{sec:bench}

\textsc{Opus-201} consists of $201$ Rust problems generated by prompting Claude Opus with a structured template specifying the problem tier, required signature, and a set of \texttt{\#[test]} cases. Every problem was compiled and executed against a reference solution; problems whose reference solution did not compile or pass its own tests were rejected. The six tiers and their weights appear in Table~\ref{tab:tiers}.

Tier & Description & Problems & Weight \\
\midrule
T1 & Basic data structures, syntax    & 108 & 1 \\

For each problem, a candidate solution is inserted into a standard Cargo crate skeleton, \texttt{cargo test} is invoked, and the run is marked \emph{passed} iff all tests pass within a 30-second wall-clock budget. Listing~\ref{lst:example} shows a representative T1 problem.

\begin{figure}[h]
\begin{lstlisting}[language=Rust,caption={\texttt{opus-ring-buffer} (T1): instruction, starter, and tests.},label={lst:example}]
// INSTRUCTIONS: Implement a fixed-capacity ring buffer. When full,
// `push` overwrites the oldest element. `peek` returns the oldest
// without removing it.

// src/lib.rs (starter -- candidate replaces todo!()s):
pub struct RingBuffer<T> { /* your fields */ }
impl<T> RingBuffer<T> {
    pub fn new(capacity: usize) -> Self { todo!() }
    pub fn push(&mut self, item: T)     { todo!() }
    pub fn pop(&mut self) -> Option<T>  { todo!() }
    pub fn peek(&self) -> Option<&T>    { todo!() }
    pub fn len(&self) -> usize          { todo!() }
    pub fn is_full(&self) -> bool       { todo!() }
    pub fn capacity(&self) -> usize     { todo!() }
}
// tests/opus_ring_buffer.rs (ground truth):
#[test] fn overwrite_on_full() {
    let mut buf = RingBuffer::new(3);
    buf.push(1); buf.push(2); buf.push(3); buf.push(4); // overwrites 1
    assert_eq!(buf.pop(), Some(2));
    assert_eq!(buf.pop(), Some(3));
    assert_eq!(buf.pop(), Some(4));
}  // ... five more tests
\end{lstlisting}
\end{figure}

\section{Method}
\label{sec:method}

\paragraph{Self-play loop.}
At each iteration, the current model samples one candidate solution per problem at a fixed temperature. Each candidate is dropped into a standard Cargo crate and scored by \texttt{cargo test}. Every passing $(\mathit{problem}, \mathit{solution})$ pair is appended to an accumulated training set $D$, deduplicated by problem slug. Fine-tuning always starts from the base model $M_0$, never the previous iteration, which prevents catastrophic forgetting and keeps the contribution of $D$ honest.

\paragraph{Training configuration.}
Our headline result uses full-parameter supervised fine-tuning of Qwen2.5-Coder-0.5B-Instruct on $D$, with a 4-bit quantized base to fit in 24\,GB VRAM, lr $=5\times 10^{-5}$, 3 epochs, chat-template target tokens only in the loss. We also report two LoRA ablations (rank 8 and rank 32) under the same data and schedule to isolate the effect of adapter capacity. All runs took between 5 and 45 minutes on one RTX 3090; the full SFT run is the longest.

\paragraph{Inference.}
All benchmark runs use \texttt{llama.cpp}'s \texttt{llama-server} serving a Q4\_K\_M GGUF export of the fine-tuned weights via its OpenAI-compatible chat-completion endpoint, 8192-token context. pass@1 uses the default temperature; pass@$k$ uses temperature $0.7$ with $k$ independent samples per problem, marked passed if any sample passes.

The full-SFT configuration lifts pass@1 by $14.9$ percentage points ($11\times$ relative). Adapter capacity matters at this scale: LoRA rank 8 captures a fifth of the full-SFT gain, LoRA rank 32 captures two-fifths, and full parameter updates capture the rest.

\subsection{Self-Play Convergence and Data Saturation}

Figure~\ref{fig:curve} shows the conservative LoRA-$r{=}8$ self-play loop run for five iterations, where each iteration fine-tunes the base model on all solutions the \emph{current} model has produced to date. The curve plateaus by iteration $3$ at $\sim 4.5\%$ and does not recover in the remaining iterations: the training set stops growing because the model has exhausted the set of problems it can, at its current capacity, ever produce compile-valid code for. Increasing adapter capacity (LoRA $r{=}32$, full SFT) is how the headline jump is realized---it unlocks harder problems that the $r{=}8$ adapter cannot.

\subsection{Failure-Mode Shift}

Because \texttt{cargo test} is a staged pipeline (parse $\to$ type-check $\to$ borrow-check $\to$ tests), each failure can be classified by the stage at which it occurs. Table~\ref{tab:failmode} classifies failures by string-matching diagnostic signatures from the captured output.

\midrule
Base, pass@1         & 3   & 173 & 8  & 11 & 4  \\

\bottomrule

The pass@1 comparison is the one that matters for the structural claim. Between the base model and the fine-tuned model, compile-failures drop by $65$ (from $173$ to $108$, a $38\%$ reduction) while test-failures rise by $15$ (from $8$ to $23$). Compiler-verified self-play is an efficient teacher of the Rust type system and borrow checker, and the fine-tuned model's residual failures are dominated by code that compiles but has the wrong logic---the kind of failure that unit tests catch but the type system cannot, and the target distribution for any concept-aware curriculum approach in future work. At pass@5 with five attempts, the model rescues failures from every category roughly in proportion to their pass@1 frequency, which is the behavior expected of a model whose sample distribution is broad rather than concentrated.

\section{Discussion}

\paragraph{Why the Rust compiler helps so much.}
Every passing sample in our training set has already been filtered by (i) parser, (ii) type checker, (iii) borrow checker, and (iv) unit tests. Three of those four filters are unavailable for free in Python-centric self-play. On base 0.5B, the parse/type/borrow filters alone eliminate $173/201$ candidate solutions; only $13/201$ survive to the test stage. Fine-tuning on the survivors disproportionately rewards code that plays well with the compiler, and this is the structural knowledge that the data gap most obviously reflects.

\paragraph{Tier ceiling.}
Figure~\ref{fig:tier} shows per-tier pass rates. Gains concentrate on T1--T3 (basic structures, debugging, and algorithmic problems); the fine-tuned 0.5B solves $0$ problems on T4--T6 at pass@1 because the base model itself cannot seed any passing solutions there. Self-play cannot lift a tier that the base model never enters. Breaking that ceiling requires either a larger base model or a targeted curriculum that re-introduces the hard-tier knowledge externally---a direction we leave to future work.

\paragraph{Limitations.}
(i) \textsc{Opus-201} was generated by Claude Opus; the Opus ``ceiling'' of $88.6\%$ therefore reflects some residual stylistic overlap and should not be read as an upper bound on our method. (ii) We fine-tune only Qwen2.5-Coder-0.5B-Instruct; the transfer to DeepSeek-Coder and StarCoder variants is untested. (iii) The failure classifier in Table~\ref{tab:failmode} relies on string-matching rustc diagnostics and may misclassify a few edge cases.

\section{Reproducibility}

Every number in Tables~\ref{tab:main} and \ref{tab:failmode} is regenerated by the following three commands from the repository root:

\begin{lstlisting}[language=bash]
# (1) Serve a fine-tuned GGUF via llama.cpp.
llama-server -m selfplay_runs_v2/models/full_ft.gguf \
    --port 8081 -c 8192 --host 127.0.0.1

# (2) Run the 201-problem benchmark.
cargo run --release --bin paper-bench -- score-local \
    --server-url http://127.0.0.1:8081 \
    --name qwen-0.5b-full-ft \
    --output results/qwen-0.5b-full-ft.json

# (3) Regenerate the figure from all result JSONs.
python crates/tempo-x402-paper/scripts/plot_figures.py
\end{lstlisting}

The base, LoRA-$r{=}8$, LoRA-$r{=}32$, and full-SFT GGUF checkpoints are included in the release. A clean reproduction of the full pipeline---fine-tune, export, benchmark---from the 122-example training set takes about 90 minutes on a single RTX 3090.
